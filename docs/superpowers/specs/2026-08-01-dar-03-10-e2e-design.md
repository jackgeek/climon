# DAR-03 through DAR-10 E2E Automation Design

## Goal

Extend the cross-platform E2E harness from DAR-01 and DAR-02 to DAR-03 through
DAR-10. The scenarios must test the externally visible daemon-actor contracts
on macOS, Linux, and Windows using deterministic harness controls rather than
literal installed-PWA, DevTools, or shell-tool workflows.

The work also introduces descriptive subcheck titles for every DAR scenario,
including DAR-01 and DAR-02, so reports identify the behavior that failed
without sacrificing stable machine-readable identifiers.

## Scope

This phase will:

- register one typed scenario for each DAR-03 through DAR-10;
- add reusable browser, PTY, process, socket, metadata, and fixture capabilities;
- extend the Rust fixture only with deterministic protocols needed by the DAR
  contracts;
- add descriptive titles to every DAR-01 through DAR-10 subcheck;
- run the complete suite in the existing macOS, Ubuntu, and Windows CI matrix;
- preserve exact platform expectation governance and failure evidence;
- document the native Windows and WSL commands used after the branch is merged
  into `fix/daemon-actor-release-gate`.

This phase will not automate browser installation UI, desktop window managers,
DevTools UI, or platform shell commands when an equivalent deterministic
process/API control can exercise the same contract.

## Architecture

The existing `ScenarioDefinition`, isolated runtime supervisor, expectation
policy, evidence layout, and reporters remain the top-level architecture.
DAR-03 through DAR-10 are separate scenario modules with their own ordered
subcheck contracts and fresh runtimes.

Shared behavior belongs in focused capabilities:

- a multi-surface browser driver for independent desktop and simulated-PWA
  identities;
- controller and terminal-readiness observations;
- live daemon socket clients, including an intentionally non-reading client;
- shell-free session-host process discovery and signaling;
- metadata, status, output, exit, and socket-cleanup assertions;
- deterministic fixture modes for full-screen repaint, attention changes,
  title/progress sequences, lifecycle exits, sustained output, and signal
  holding.

Scenario modules may consume these capabilities but must not import orchestration
from another scenario. Platform differences remain expectation-policy data,
not success-shaped fallback branches.

## Cross-Platform Model

All scenarios run in the existing macOS, Linux, and Windows workflow matrix.

The PWA surface in DAR-03 is represented by a second isolated Chromium context
and page with an independent viewer identity, phone-sized viewport, and
standalone-style display settings. The contract under test is controller
identity and newest-take-control priority, not browser installation UI.

Unix DAR-09 signal checks send real `SIGINT` and `SIGTERM` to the freshly
resolved `climon __session <id>` host PID. Windows uses native forced host
termination and the real ConPTY console-resize path. Host discovery must never
substitute metadata `daemonPid`, which identifies the monitored child.

Unsupported platform-specific subchecks must be declared through the existing
expectation policy with an exact reason, tracking reference, review date, and
allowed failed subchecks.

## Descriptive Subcheck Contracts

Every subcheck has:

- `name`: a stable kebab-case machine identifier;
- `title`: a concise description of the behavior being asserted.

Example:

- name: `same-size-browser-control-jiggle`
- title: `Jiggles both terminal dimensions when same-size browser control is acquired`

Scenario definitions declare the ordered `{ name, title }` contract. Runtime
validation rejects missing, duplicate, unknown, or reordered subchecks.

Console and Markdown output show the descriptive title and stable identifier.
JSON stores both. JUnit uses the descriptive title as the testcase name and
retains the stable identifier as a property. DAR-01 and DAR-02 receive titles
as part of this phase so all reports are consistent.

## Scenario Contracts

### DAR-03: Controller Handoff and Local Reclaim

Start an attached full-screen fixture with the local terminal as controller.
Open a desktop dashboard surface and take control, then open a simulated-PWA
surface and take control. Verify the newest surface wins, displaced surfaces
cannot send ordinary input, the shared PTY follows the active controller size,
and local Space reclaims control and restores local sizing.

Evidence includes controller identity history, PTY sizes, local PTY input and
output, both browser traces, and fixture markers.

### DAR-04: Restore and Same-Size Repaint Jiggle

Use a frame-caching full-screen fixture that reports every resize and repaint.
Exercise both local restore and same-size browser take-control. Verify the
daemon emits a one-column and one-row shrink followed by restoration across
separate ticks, and that the fixture presents a complete authoritative frame
after the final size.

Descriptive failures distinguish the first jiggle leg, second jiggle leg,
both-dimension change, tick separation, and final repaint.
The ordered DAR-04 subchecks are:

- `Resizes the shared PTY when a larger browser acquires control`
- `Jiggles both terminal dimensions when local control is restored`
- `Repaints a complete authoritative frame after local restore`
- `Jiggles both terminal dimensions when same-size browser control is acquired`
- `Repaints a complete authoritative frame after same-size control handoff`

### DAR-05: Attention, Acknowledgement, and Resize Stickiness

Use an isolated short attention interval. Hold a deterministic static screen
until the session becomes `needs-attention`, acknowledge the current token from
the dashboard, produce a persistent visible-body change, verify the session
returns to `running` and re-flags after a new idle interval, then resize without
program output and confirm attention remains set. A second current-token
acknowledgement must succeed.

Stale-token rejection and current-token acceptance are asserted separately.

### DAR-06: Terminal Title and Progress Capture

Drive a fixture protocol that emits OSC 0, OSC 2, determinate progress, clear,
indeterminate, error, and warning states on command. Verify the sequences still
reach terminal output, metadata updates after debounce, dashboard title and
progress UI match metadata, and clear operations remove persisted/UI state.

### DAR-07: Ordered Exit Finalization

Run deterministic fixture commands that emit early output and exit with 0 and
7. Verify output is not lost, final scrollback is persisted, metadata reaches
`completed` or `failed` with the exact exit code and `completedAt`, clients
receive terminal completion, and the session listener is closed. Unix-domain
socket runs additionally verify removal of the socket file; loopback-TCP runs
verify the recorded port no longer accepts connections.

### DAR-08: Slow Viewer Isolation

Run a bounded high-volume fixture with an attached local surface and healthy
browser. Add a daemon client that completes the protocol handshake and then
intentionally stops reading. Verify the stalled client's bounded route is
evicted without blocking the coordinator, PTY reader, local output, or healthy
browser. The healthy surface must observe markers emitted both before and after
the stalled client fails.

This deterministic non-reading client replaces manual DevTools throttling while
testing the same per-client isolation contract.

### DAR-09: Signals, Host Termination, and Resize

Run a long-lived fixture and resolve the detached session-host PID from process
command lines immediately before each termination action. On Unix, exercise
real `SIGINT`, `SIGTERM`, repeated-signal idempotency, and attached resize. On
Windows, force-terminate the host and exercise the real ConPTY resize poller.

Verify the monitored child is reaped, metadata reaches the expected terminal
state, clients and sockets close, local terminal state is restored where
attached, and no stale host PID is reused.

### DAR-10: Actor-to-Legacy Rollback

Run the same deterministic command with `CLIMON_SESSION_ENGINE` unset,
`legacy`, and `actor`. Compare output, exit code, metadata, and final
scrollback. Then run attached and headless invalid-engine cases and verify the
exact diagnostic:

`invalid CLIMON_SESSION_ENGINE '<value>'; expected 'legacy' or 'actor'`

The headless invalid case must capture the error from the detached session log
and confirm no live session starts.

## Fixtures and Drivers

Fixture extensions must remain small command protocols rather than one
monolithic actor exerciser. Each protocol emits versioned, line-oriented
markers and accepts explicit commands. Fixture tests cover parser behavior,
real node-pty transport, disconnect handling, and exit semantics.

Browser extensions support multiple isolated surfaces, viewport changes,
take-control actions, attention acknowledgement, title/progress inspection,
terminal text/input, screenshots, console history, failed requests, and
per-surface tracing.

Process discovery is shell-free. Platform adapters may invoke fixed executable
and argument arrays such as `ps` on Unix or PowerShell/CIM on Windows, parse
complete command lines, require exactly one matching host, and re-resolve before
every signal.

## Synchronization and Error Handling

All waits are condition-based and bounded by scenario and subcheck deadlines.
No scenario depends on live output appearing in final-persistence files.
Running output is observed through PTY, browser/daemon protocols, or live
metadata as appropriate; persisted files are asserted only after finalization.

A failed prerequisite produces an explicit dependent-subcheck failure naming
the unavailable state. It does not silently skip the assertion. Cleanup runs
independently and cleanup failures remain blocking even when the scenario
already failed.

Each case preserves partial evidence:

- PTY input/output and screen snapshots;
- fixture command/marker transcripts;
- metadata snapshots and status transitions;
- daemon, client, server, and session logs;
- process and session ledgers;
- controller and PTY-size histories;
- browser traces, screenshots, console messages, and failed requests;
- socket probes and signal/termination records.

## Testing

Unit tests validate scenario orchestration, dependency failures, exact
subcheck ordering/titles, platform adapters, process discovery, socket probes,
and expectation governance.

Fixture protocol tests use real node-pty under Node 24. Browser-driver tests use
the existing typed seams, with focused real-browser coverage where semantic
hooks or multiple contexts are involved.

Local macOS verification runs:

```sh
bun run harness -- doctor
bun run harness -- run DAR-01 DAR-02 DAR-03 DAR-04 DAR-05 DAR-06 DAR-07 DAR-08 DAR-09 DAR-10 \
  --artifact-root .test-tmp/e2e-harness/macos
```

The GitHub Actions matrix runs the same scenario set on macOS, Ubuntu, and
Windows, uploads per-platform evidence, and aggregates exact platform results.

## Integration and Release-Gate Flow

After implementation:

1. Push the E2E branch and run CI on macOS, Ubuntu, and Windows.
2. Fix harness defects and change platform expectations only from captured
   evidence.
3. Merge the E2E work into `fix/daemon-actor-release-gate`.
4. Run the complete suite directly on native Windows and again inside WSL,
   using separate artifact roots.
5. Use those Windows and WSL artifacts as daemon-actor release-gate evidence
   and fix unexpected failures on the actor branch.

The current GitHub token can push but cannot create pull requests. If that
permission remains unchanged, the branch and compare URL must be handed off for
the PR/merge operation.
